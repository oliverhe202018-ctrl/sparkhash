## 1. S_STAR 控制器数学模型与调控机制

`MinerV1.sol` 采用自适应指数移动平均（EMA）控制器，其核心调控逻辑在 `sync(maxSteps)` 中执行（第 294 至 303 行）：

```solidity
n++;
uint256 shares = (n >= 2) ? totalShares[n - 2] : S_STAR;
ema = (ema + shares) / 2;
uint256 t = target[n - 1];
if (t > EASIEST) t = EASIEST;
uint256 nt = (ema == 0) ? (t * 125 / 100) : (t * S_STAR / ema);
if (nt > t * 125 / 100) nt = t * 125 / 100;
if (nt < t * 100 / 125) nt = t * 100 / 125;
if (nt > EASIEST) nt = EASIEST;
if (nt < HARDEST) nt = HARDEST;
target[n] = nt;
```

### 控制器五大核心动力学特征：
1. **两轮反馈滞后 (`n - 2`)**：第 $n$ 轮调节采用的是第 $n-2$ 轮的实际提交份额 `totalShares[n - 2]`，给节点留出充分的共识结算与出块时间；
2. **离散整数 EMA 滤波**：$\text{EMA}_n = \lfloor \frac{\text{EMA}_{n-1} + S_{n-2}}{2} \rfloor$，记忆衰减因子为 $\alpha = 0.5$；
3. **比例调节法则**：若 $\text{EMA} > S^*$，则 $nt < t$（难度提升，目标哈希值变小）；若 $\text{EMA} < S^*$，则 $nt > t$（难度下降，目标哈希值变大）；
4. **单轮限幅保护 (Rate Limiting)**：单轮目标值调整被强制锁定在 $[0.8 \times t, 1.25 \times t]$ 区间。对应难度位数单轮最大变化幅度为：
   $$\Delta d_{\max} = \log_2(1.25) \approx 0.3219\text{ 位/轮}$$
5. **绝对边界硬锁**：无论网络算力如何过剩或枯竭，难度绝不低于 32 位（$2^{224}$），亦绝不高于 35 位（$2^{221}$）。

### 2.1 均衡难度位数理论推导模型
设网络在 32 位基准难度下的全网总潜在份额为 $S_{\text{pot}} = A \times \bar{s}$。
- 若 $A \times \bar{s} \le S^*$：全网算力不足以支撑 $S^*$ 目标，控制器持续要求降难度，触发下限截断，均衡难度恒为 **32.00 位**；

  $$d_{\text{eq}} = \min\left(35.00, \max\left(32.00, 32.00 + \log_2\left(\frac{A \times \bar{s}}{S^*}\right)\right)\right)$$

## 3. 难度爬升动力学与 CPU 用户生存空间分析

### 3.1 从 32 位升至 35 位所需轮数严格推导

当网络算力出现暴增（例如大规模 GPU 集群突发涌入，使每轮潜在份额激增至远超 $8 \times S^*$ 时），难度需要从 32 位（$T_0 = 2^{224}$）升至 35 位（$T_{\text{hardest}} = 2^{221}$）：

1. **总目标收缩比**：$\frac{T_{\text{hardest}}}{T_0} = \frac{2^{221}}{2^{224}} = 2^{-3} = \frac{1}{8} = 0.125$；
2. **单轮调节下限**：合约规定单轮目标值最小下调至 $t \times \frac{100}{125} = 0.8 \times t$；
3. **理论最少下调步数**：
   $$0.8^k \le 0.125 \implies k \ge \frac{\ln(0.125)}{\ln(0.8)} = \frac{-2.07944}{-0.22314} \approx 9.32 \implies k = 10\text{ 步}$$
4. **EMA 延迟吸收过程**：
   - Epoch 0：突发涌入开始，当轮结算产生海量份额；
   - Epoch 1：`sync(1)` 读取 $n=1$，按代码规约使用默认 `S_STAR`，EMA 保持 50,000，目标不调整；
   - Epoch 2：`sync(1)` 读取 $n=2$，首次读入 Epoch 0 的海量份额，EMA 骤升，触发首次 0.8x 顶格下调；
   - Epoch 3 ~ 12：连续 9 轮执行 0.8x 下调；
   - Epoch 13：第 10 次下调由于 $0.8^{10} \approx 0.1074 < 0.125$，触发 `HARDEST` 边界截断，正式锁死在 35 位。
5. **结论**：在最极端突发算力冲击下，难度从 32 位爬升至 35 位硬顶需要 **11 到 13 轮**（合约单元测试 `test_Convergence11EpochsUnder10xHashrateSurge` 实测在第 13 轮锁定，耗时 13 小时）。

### 3.2 32 位 vs 35 位下 CPU 用户的期望份额与填满率断崖

## 4. 核心决策结论与治理推荐

### 4.1 首版主网参数强烈推荐：`S_STAR = 50,000`

我们完全赞同并将主网创世参数确立为 **`S_STAR = 50,000`**。核心依据如下：

1. **完美的冷启动保护区**：
   在上线初期的数周至数月内，若网络活跃地址在 $1,000 \sim 8,000$ 之间，全网份额处于 $2,000 \sim 48,000$ 区间，均小于 50,000。难度将**稳稳锁定在 32 位**，确保所有早期 CPU 用户享有 34.8% 的高填满率与 87.7% 的超高中奖率，实现社区爆发式自裂变。
2. **避免过早硬顶窒息**：
   若设为 5,000 或 10,000，只要有 834 ~ 1,667 个 GPU 地址进场，难度就会被瞬间顶进 35 位硬顶，让 CPU 矿工在第 1 周即遭驱逐；而 50,000 留出了 $8,334$ 个全额 GPU 地址或 $25,000$ 个 CPU 地址的广阔安全缓冲区。
3. **与经济发行规模完美自洽**：
   首日基础排放为 $D_0 = 3,000,000$ Token，单轮配额为 125,000 Token。当全网总份额达到 $S^* = 50,000$ 时，平均每份有效份额价值约为 $2.5$ 枚 Token，计价单位极其清晰直观，符合代币经济学心理学。

### 4.3 上线后参数调整标准作业流程 (Post-Launch Governance SOP)

若未来网络规模发生重大跃迁，需要调整 `S_STAR` 时，必须严格遵循以下治理规约：

#### 1. 监控触发阈值
- **调大 S_STAR 触发条件**：连续 72 轮（3 天）全网平均活跃地址数 $> 30,000$，且难度持续触碰 34.5 位以上，导致 CPU 用户平均空轮率 $> 60\%$ 时，应提议上调 `S_STAR`（如由 50,000 上调至 100,000）。
- **调小 S_STAR 触发条件**：全网地址大规模撤退（活跃地址 $< 2,000$），且代币价格大幅升值导致单份份额被极少数巨鲸垄断时，可下调 `S_STAR`（如由 50,000 下调至 20,000）。

#### 2. 合约治理执行与边界防护
依据 `MinerV1.sol` 第 385 行：
```solidity
function setSStar(uint256 newSStar) external override {
    if (msg.sender != admin) revert OnlyAdmin();
    if (newSStar < 1_000 || newSStar > 1_000_000) revert ParameterOutOfBounds();
    uint256 old = S_STAR;
    S_STAR = newSStar;
    emit SStarUpdated(old, newSStar);
}
```
- **权限与时间锁**：仅 `admin`（绑定为 Timelock 治理合约）可调用，具有法定公示期；
- **边界硬约束**：新值必须严格位于 $[1,000, 1,000,000]$ 区间；
- **快照隔离安全机制**：合约在每轮结算时均通过 `epochSStar[n] = S_STAR` 固化当前轮快照。**对 `S_STAR` 的任何修改绝对不会追溯影响任何过去已结算但未领取的历史奖励**。

#### 3. 渐进式调整原则
- 单次调整幅度严禁超过现行值的 **50%**（例如 50,000 $\to$ 75,000，或 50,000 $\to$ 35,000），防止控制器因目标断崖而引发剧烈震荡；
- 两次调整之间的间隔时间不得少于 **48 轮**（2 天），以完整观察一个提款冷却周期内的算力重平衡效应。
