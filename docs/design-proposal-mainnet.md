# PoolCoin 主网升级设计提案 (Mainnet Design Proposal)

---

## 1. 概述与核心背景

本提案针对 PoolCoin 在 BNB Smart Chain (BSC) 测试网（Chain ID: 97）实测阶段暴露出的关键机制问题，提出面向主网部署的系统性工程与经济学升级方案。

在测试网第一阶段的运行中，系统的 PoW 份额提交、验证与合约结算流程顺利跑通，但实测数据与深层代码审计揭示了三大核心机制痛点：
1. **种子初始化时效性与出块时间脱节**：BSC 出块时间已由历史上的 3 秒演进至约 0.45 秒，EVM 的 256 块 `blockhash` 回溯窗口急剧收缩至 115 秒，导致跨轮种子初始化极易因超时而返回 0，阻塞全网挖矿。
2. **奖励记账守恒逻辑不够严谨**：原设计中粗糙的“已领取 + UnallocatedReward = 配额”未能区分静态结算与动态提领，忽视了 EVM 存储不可遍历性对单地址 20% 上限截断的约束。
3. **GPU 算力挤压与难度区间失真**：现行难度区间（34 到 36 位）与 CAP=15 设定下，单台 GPU（1.3 GH/s）相较于 CPU 仍具有过高优势，且在算力较小启动期容易导致大量轮次无有效份额产出。

本提案严格在保持代理合约（ERC-1967 Proxy）存储布局 100% 向前兼容的前提下，提出闭环解决方案，并辅以确定性的数学证明与离线仿真数据支撑。

## 2. 基础运行环境与出块时间校准

### 2.1 测试网实测数据推导

根据 BSC 测试网第一阶段真实链上交易区间的实测数据：
- **起始区块**：`140937209`（时间戳：`1793872561`）
- **结束区块**：`140945027`（时间戳：`1793876079`）
- **区块差额**：$\Delta \text{Block} = 140945027 - 140937209 = 7818\text{ 块}$
- **时间跨度**：$\Delta T = 1793876079 - 1793872561 = 3518\text{ 秒}$

实测平均出块时间为：
$$T_{\text{block}} = \frac{3518\text{ 秒}}{7818\text{ 块}} \approx 0.449987\text{ 秒/块} \approx 0.45\text{ 秒}$$

### 2.2 主网官方文档考证

查阅 BNB Chain 官方技术文档：
- **官方文档来源**：[BNB Chain Official Documentation - BSC Overview](https://docs.bnbchain.org/bnb-smart-chain/overview/)
- **官方权威论述**：
  > "BSC block time is approximately **0.45 seconds** (reduced from 3s through the Lorentz, Maxwell, and Fermi hardforks), ensuring near-instant transaction confirmations and an overall smoother user experience."

由此确认：**BSC 主网与测试网均已全面进入 0.45 秒亚秒级出块时代，历史遗留的 3 秒/块假设必须彻底废除**。

### 2.3 256 块 EVM 窗口的技术冲击分析

EVM 原生操作码 `blockhash(uint256 blockNumber)` 仅能访问距离当前区块最近的 256 个历史块哈希，超出此范围统一返回 `bytes32(0)`。
- **历史 3 秒出块期**：$256 \times 3\text{s} = 768\text{ 秒} \approx 12.8\text{ 分钟}$。
- **现行 0.45 秒出块期**：$256 \times 0.45\text{s} = 115.2\text{ 秒} \approx 1.92\text{ 分钟}$。

这一物理客观变化对系统产生致命影响：
在单轮时长 $T_{\text{epoch}} = 3600\text{ 秒}$（1 小时）的机制下，新轮次起始区块的哈希**仅在轮次刚开始的前 115 秒（占整轮时长的 3.2%）内有效**！
一旦轮次切换超过 1.92 分钟且没有交易调用初始化种子，任何后续发起的常规 `blockhash` 查询都将返回 `0x0`。若合约强行使用返回值，将导致 `epochSeed[e] = 0`，全网矿工在提交时触发 `SeedNotInitialized()` 拒绝交易，挖矿陷入死锁。

因此，**跨轮确定的哈希链（Hash Chain）后备机制绝非极端边缘用例，而是必须 100% 具备确定性保证的核心通道**。

### 3.2 彻底更正 "槽 38 矛盾"

- **原误解产生原因**：前期讨论中偶有提及“epochSeed 存储在槽 38，与 `__gap` 冲突”。
- **真实代码事实澄清**：
  1. `epochSeed` 从首个部署版本起，其实际槽位始终固定在 **Slot 9**；
  2. `__gap` 数组定义为 `uint256[47] private __gap;`，起始槽位为 **Slot 20**，连续覆盖至 **Slot 66**（$20 + 47 - 1 = 66$）；
  3. 所谓“槽 38”，实际上位于 `__gap[18]`（$20 + 18 = 38$），属于预留槽位内部，并不存在任何槽位冲突。
- **升级无损兼容规范**：
  由于 `MinerV1` 部署在 ERC-1967 Proxy 代理合约之后，若主网或 V2 升级需要增加持久化变量（例如用于记录未分配配额的 `unallocatedRewards` 或储备金库地址）：
  - **正确做法**：直接从 Slot 20 开始顺序占用，并将 `__gap` 的大小相应缩减。例如新增一个 `mapping(uint256 => uint256) public unallocatedGap;` 占据 Slot 20，同时将 `__gap` 声明改为 `uint256[46] private __gap;`（起始槽位后移至 Slot 21）。
  - **结论**：无需重新部署代理合约，状态完全无缝继承。

## 4. 议题一：种子初始化方案设计

### 4.1 方案设计目标

针对 115 秒后 `blockhash` 返回 0 的物理特性，设计**免许可、抗抢跑、带补齐上限**的种子初始化机制：
1. **自动补齐**：允许一次交易补齐中间所有缺失的未初始化轮次；
2. **后备哈希链**：对于已超出 256 块窗口的历史轮次，采用确定性哈希链递归推导；
3. **矿工客户端自愈**：矿工扫描到目标轮次 `epochSeed == 0` 时，在提交份额前自动组合或先发初始化交易。

### 4.2 种子生成算法规范

对于轮次 $e$（起始区块为 $B_{\text{start}}(e) = \text{START} + e \times \text{EPOCH\_BLOCKS}$）：
```solidity
function initEpochSeed(uint256 e) public returns (uint256) {
    if (e > epoch()) revert EpochNotStarted();
    if (epochSeed[e] != 0) return epochSeed[e];

    // 确保前序轮次种子已存在；若缺失则带上限递归补齐 (最多回溯 MAX_SEED_STEPS 步)
    if (e > 0 && epochSeed[e - 1] == 0) {
        _backfillSeeds(e - 1);
    }

    uint256 targetBlock = getStartBlock(e);
    uint256 seed;

    if (block.number > targetBlock && block.number <= targetBlock + 256) {
        // 窗口期内 (115 秒内)：直接使用真实区块哈希
        bytes32 bh = blockhash(targetBlock);
        if (bh != bytes32(0)) {
            seed = uint256(bh);
        }
    }

    // 窗口期外或 blockhash 不可用：无缝降级为前序种子哈希链
    if (seed == 0) {
        uint256 prevSeed = (e == 0) ? uint256(keccak256("POOLCOIN_GENESIS_SEED")) : epochSeed[e - 1];
        seed = uint256(keccak256(abi.encodePacked(prevSeed, e, block.chainid)));
    }

    epochSeed[e] = seed;
    emit EpochSeedInitialized(e, seed, block.number);
    return seed;
}
```

### 4.3 攻击面与安全性论证

#### A. 是否可被抢跑或操控 (Front-Running & Manipulation)
- **区块生产者 (Validator) 操纵性**：
  在 115 秒窗口内，验证者理论上可以通过调整区块内容来微调 $B_{\text{start}}$ 的哈希。然而，BSC 上验证者轮换频繁且单区块出块仅 0.45 秒，验证者放弃区块奖励去操控特定 PoW 种子的机会成本极大。
- **后备哈希链的确定性**：
  一旦进入哈希链模式，`seed = keccak256(prevSeed, e, chainid)` 为纯数学伪随机数，输入完全不可变。**任何第三方调用得到的种子完全一致**，抢跑者无法改变计算结果，也无法通过插队获取不当利益。

#### B. 补齐的 Gas 消耗上限
- 引入常量 `MAX_SEED_STEPS = 24`（允许一次补齐 1 天的缺失轮次）。
- 每次写入 mapping 需要 1 次冷写（20,000 gas）或热写，单轮补齐消耗约 26,000 gas。
- 24 轮补齐总 Gas 约为 $24 \times 26,000 \approx 624,000\text{ gas}$，远低于 BSC 区块 Gas 限制（140M gas），完全杜绝 Gas 耗尽 DoS 风险。

#### C. 矿工客户端自动化工作流
- 矿工客户端（`miner.py`、`miner_gpu.py`）在启动轮次监听时，首先调用只读 RPC 查询 `epochSeed(e)`；
- 若返回 `0`，矿工客户端自动构造并签名 `initEpochSeed(e)` 交易广播上链，等待 1 个区块（0.45s）确认后拉取有效种子开跑；
- 形成“无人值守、自治自愈”的去中心化闭环。

## 5. 议题二：奖励守恒与四桶分桶记账模型

### 5.1 守恒恒等式重构

原有提案中将守恒表述为“已领取 + UnallocatedReward = 配额”，未能清晰表达合约内部的资金生命周期。主网设计重构为**四桶分桶守恒模型（Four-Bucket Conservation Model）**：

对于任意已结束轮次 $e$，设其有效铸造配额为 $Q = \text{effectiveQuota}(e)$，在任意时间戳 $t$，全网资金严格满足：
$$Q \equiv B_1(t) + B_2(t) + B_3 + B_4$$

各桶定义与数学性质如下：

| 分桶编号 | 资金属性 | 状态性质 | 确定时刻与 Gas 复杂度 | 经济学含义 |
| :--- | :--- | :--- | :--- | :--- |
| **$B_1(t)$** | **已领取 (Claimed)** | 动态递增 | 随矿工调用 `claim(e)` 逐步增加 ($O(1)$) | 已真实铸造并转移至矿工钱包的代币 |
| **$B_2(t)$** | **可领未领 (Entitled Unclaimed)** | 动态递减 | 终态确定，但在提取前为隐式存在 | 矿工合法赚取、随时可通过 `claim(e)` 提走的代币 |
| **$B_3$** | **$W_{\min}$ 稀释未分配 (Dilution Gap)** | **绝对静态** | **`sync(e)` 结算时 100% 确定 ($O(1)$)** | 因全网有效权重不足 $W_{\min}$ 导致的通缩配额差额 |
| **$B_4$** | **20% 阈值截断溢出 (Cap Overflow)** | 逐步物化 | **仅在矿工调用 `claim(e)` 时逐笔确定** | 算力大户触碰单地址 20% 硬顶后被截断的代币 |

### 5.2 为什么 $B_4$ 无法在 `sync` 阶段确定（防范 Gas DoS）

深入分析 EVM 底层机制：
- 矿工权重存储在嵌套映射中：`mapping(uint256 => mapping(address => uint256)) userWeight`。
- EVM 映射类型不可遍历。若要在 `sync(e)` 时计算出 $B_4 = \sum_i \max(0, r_i^{\text{raw}} - \text{maxAmt})$，合约必须在提交份额时用动态数组记录所有矿工地址，并在 `sync` 时循环遍历。
- **安全灾难**：若一轮中有 5000 名微型矿工提交份额，遍历数组需要消耗数千万 gas，直接导致 `sync(e)` 无法打包，整个协议因无法推进轮次而瘫痪！
- **正确实现**：$B_4$ 必须作为流式变量，在每位矿工调用 `claim(e)` 时在 $O(1)$ 内计算差额 $\Delta B_4(i) = r_i^{\text{raw}} - r_i$。
### 5.3 $W_{\min}$ 稀释缺口 $B_3$ 的数学闭环

在轮次 $e$ 结束时，全网总权重 $tw = \text{totalWeight}[e]$ 已经完全固定（因提交必须在轮内完成）。
分母定义为 $D = \max(tw, W_{\min}(e))$。
所有矿工的理论应发总额为：
$$\sum_{i} r_i^{\text{raw}} = \sum_{i} \frac{Q \cdot u_i}{D} = \frac{Q \cdot \sum_i u_i}{D} = \frac{Q \cdot tw}{\max(tw, W_{\min})} = Q \cdot \min\left(1, \frac{tw}{W_{\min}}\right)$$

因此，由 $W_{\min}$ 保底稀释导致的未分配缺口为：
$$B_3 = Q - \left\lfloor \frac{Q \cdot \min(tw, W_{\min})}{W_{\min}} \right\rfloor$$
该公式仅依赖 `totalWeight[e]`、`wMin(e)` 和 `effectiveQuota(e)` 三个标量，可在 `sync` 中耗费极低 gas（仅数千 gas）瞬间算出并记录。

### 5.4 未分配代币处置方案的博弈对比

针对 $B_3$ 及后续沉淀的 $B_4$，评估三种主流经济学处理模型：

| 处理方案 | 机制说明 | 优势 | 潜在博弈风险与缺陷 | 综合建议 |
| :--- | :--- | :--- | :--- | :--- |
| **方案 A：默认不铸造 (通缩模型)** | 合约不调用 `token.mint`，这部分代币永远留在未铸造状态。 | 机制极度极简；天然硬通缩；提升全网持币人每币价值；零代码攻击面。 | 在冷启动期若参与人数少，实际流通代币释放慢于原定曲线。 | **强力推荐 (默认采用)** |
| **方案 B：滚入下一轮配额 (Rollover)** | 将 $B_3$ 追加至第 $e+1$ 轮的有效配额中 ($Q_{e+1} = Q + B_3$)。 | 保证总量按恒定时间全部释放给真实矿工。 | **极度危险（算力突发捕食攻击）**：大算力 GPU 巨鲸可故意在某轮不挖矿让其滚存，累积数倍奖励后在下一轮瞬间倾泻算力霸占全池，严重剥夺小矿工。 | **强烈否决** |
| **方案 C：自动铸造至流通池/储备库** | 将未分配代币铸造给由 Timelock 控制的 Reserve 储备合约。 | 沉淀国库资金，可用于未来流动性引导、生态扶持或链上回购。 | 引入治理信任成本；若治理被黑客攻破存在抛压风险；需要编写额外金库合约。 | **可选扩展 (须加时间锁)** |

## 6. 议题三：抗 GPU 优势的参数优化与仿真分析

### 6.1 统计模型与算力仿真框架

基于泊松过程建立每轮产出数学模型：
在单轮时长 $T = 3600\text{s}$，难度为 $D\text{ 位}$（目标命中概率 $p = 2^{-D}$）下，算力为 $H\text{ H/s}$ 的矿工在单轮内发现有效 share 的期望值满足参数为 $\lambda = H \cdot T \cdot p$ 的泊松分布：
$$P(K = k) = \frac{\lambda^k e^{-\lambda}}{k!}$$
受到每轮地址份额上限 $\text{CAP}$ 的约束，矿工实际计入奖励的有效份额为 $K_{\text{valid}} = \min(K, \text{CAP})$。其对结算总权重的贡献为：
$$W = \mathbb{E}[\sqrt{K_{\text{valid}}}] = \sum_{k=0}^{\infty} P(K = k) \cdot \sqrt{\min(k, \text{CAP})}$$

针对用户提出的多维度诉求，我们在 `docs/simulation_gpu_resistance.py` 中实现了完整的离线仿真引擎。

### 6.2 Part A: 算力矩阵扫描 (CPU 1.0~5.0M vs GPU 1.3~10.0G)

扫描结果节选（详见下表）：

| 难度 (bits) | CAP | CPU 速度 | CPU 期望权重 | GPU 速度 | GPU 期望权重 | GPU 相对优势 | GPU 算力浪费率 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :---: |

### 6.4 Part C: 女巫攻击与地址拆分防线分析

若拥有 1.3 GH/s 算力的 GPU 攻击者试图通过女巫攻击，将算力均分至 $N$ 个地址以规避 CAP 限制：
- 在 32 位难度、CAP=6 下：
  - $N=1$：GPU 期望权重 2.449，占全网（100 CPU）份额 1.28%；

#### 为什么链上经济摩擦能有效击碎女巫攻击？
1. **Vault 质押资本门槛**：PoolCoin 引入质押递增机制（Ramp）。攻击者拆分 8 个地址需要准备 8 份独立的质押代币，形成巨大的资金占用与沉没成本。
2. **提交与提领的 Gas 摩擦**：
   在 BSC 上，单地址提交加提领的 Gas 消耗约为 200,000 gas。以 3 Gwei 计算，每个地址单轮消耗约 0.0006 BNB。
   拆分为 8 个地址，单轮仅链上交易手续费就激增 8 倍。当每轮单币收益不足以覆盖 Gas 成本时，女巫攻击陷入经济负收益。

### 6.6 难度控制器的调节目标、代码行号与全场景难度轨迹分析

#### A. 难度控制器的调节目标与核心代码行号
在 `src/MinerV1.sol` 中，难度控制器的设计初衷是通过负反馈动态调整目标值 `target`，使得**全网每轮（1小时）提交并有效计入合约的 PoW 份额总数平滑稳定在预设常数 $S^* = \text{S\_STAR}$（50,000 份/轮）**。

相关代码行号与实现细节如下：
- **目标常数与边界常量（`MinerV1.sol` 行 26-27，行 113-116）**：
  ```solidity
  uint256 public constant EASIEST = uint256(1) << 222;  // 34 bits
  uint256 public constant HARDEST = uint256(1) << 220;  // 36 bits
  ...
  S_STAR = 50_000;
  target[0] = EASIEST;
  ema = 50_000;
  ```
- **自适应调节核心逻辑（`MinerV1.sol` 行 286-295，位于 `sync` 函数内部）**：
  ```solidity
  uint256 shares = (n >= 2) ? totalShares[n - 2] : S_STAR;
  ema = (ema + shares) / 2;
  uint256 t = target[n - 1];
  uint256 nt = (ema == 0) ? (t * 125 / 100) : (t * S_STAR / ema);
  if (nt > t * 125 / 100) nt = t * 125 / 100;
  if (nt < t * 100 / 125) nt = t * 100 / 125;
  if (nt > EASIEST) nt = EASIEST;
  if (nt < HARDEST) nt = HARDEST;
  target[n] = nt;
  ```

**机制原理解析**：
1. **滞后 2 轮反馈与 EMA 平滑**：由于当前轮与前一轮份额仍在提交或结算中，控制器使用 $n-2$ 轮的已结算份额 `totalShares[n-2]` 进行指数平滑（权重 $\alpha = 0.5$），滤除短期算力波动杂波；
2. **比例调节比例**：新目标 $nt = t \cdot S^* / \text{ema}$。若 $\text{ema} > S^*$，则 $nt < t$（目标值变小，前导零增多，难度增加）；若 $\text{ema} < S^*$，则 $nt > t$（目标值变大，难度降低）；
3. **单轮调节幅度钳制**：单轮最大调节上限为 $+25\%$（降难上限，`t * 125/100`），下限为 $-20\%$（升难上限，`t * 100/125`）；
4. **硬性边界保护**：不论算力如何极端变化，`target` 永远被钳制在 `[HARDEST, EASIEST]` 之间。

#### C. 核心裁定：在 1000 个 CPU 加 200 个 GPU 规模下，控制器会不会到达 35 位？
**明确结论：绝对不会到达 35 位。控制器甚至连 34.1 位都无法跨越，而是会 100% 永久死锁在最易边界（当前配置的 34.0 位，或推荐配置的 32.0 位）！**

其背后的深层数学与机制证明如下：

1. **第一重绝对防线：单地址单轮份额硬顶（CAP 物理天花板）**：
   - 合约在 `submitShares` 中强制执行：`counted[e][miner] + ks.length <= CAP`；
   - 1000 个 CPU + 200 个 GPU 总计对应 **1,200 个独立矿工地址**；
   - 全网在单轮内能够被合约计入的份额总数理论极限为：
     $\text{Max Shares} = 1,200 \times \text{CAP}$
     - 当 $\text{CAP} = 15$ 时：$\text{Max Shares} = 1,200 \times 15 = 18,000\text{ 份} \ll 50,000$；
     - 当 $\text{CAP} = 6$ 时：$\text{Max Shares} = 1,200 \times 6 = 7,200\text{ 份} \ll 50,000$；
   - 只要全网矿工独立地址数不足 **3,334 个**（CAP=15 时 $50,000 / 15$）或 **8,334 个**（CAP=6 时 $50,000 / 6$），全网提交份额在物理上永远无法达到 $S^* = 50,000$！
   - 控制器观察到的 `ema` 始终只有 3,000~3,500，计算出的调节因子 $S^* / \text{ema} \approx 14 \gg 1$，每一轮都在发出“**算力严重匮乏，必须将难度降至最低**”的指令，导致 `target` 恒定触碰 `EASIEST` 上界。

2. **第二重绝对防线：无约束总算力在 35 位难度下的理论产出缺口**：
   - 退一万步假设：即便所有 GPU 矿工发动完美女巫攻击将算力无限细分至数万个地址（即完全解除 CAP 截断约束）：
   - 1000 个 2.5 MH/s CPU 总算力 $2.5\text{ GH/s}$；200 个 1.3 GH/s GPU 总算力 $260.0\text{ GH/s}$，全网总算力为 $H_{\text{total}} = 262.5\text{ GH/s}$；
   - 在 35 位难度下，挖出一个 share 需要期望 $2^{35} \approx 3.436 \times 10^{10}$ 次哈希；
   - 全网在 1 小时（3600 秒）内能够产生的全部 share 理论总期望值为：
     $\text{Expected Shares}_{35\text{-bit}} = \frac{262.5 \times 10^9 \times 3600}{2^{35}} = \frac{9.45 \times 10^{14}}{3.436 \times 10^{10}} \approx 27,502.8\text{ 份}$
   - **27,502 份依然远低于 50,000 份！**
   - 要让全网在 35 位难度下产出 50,000 份份额以维持动态平衡，全网必须具备的最低无损净算力为：
     $H_{\min} = \frac{50,000 \times 2^{35}}{3600} \approx 477.2\text{ GH/s}$
     这相当于全网必须拥有 **至少 367 台满速 1.3 GH/s GPU** 且完全无视 CAP 限制。
   - 在只有 200 台 GPU（262.5 GH/s）的无 CAP 假想下，全网的自然平衡难度也仅为：
     $D_{\text{equilibrium}} = \log_2\left(\frac{262.5 \times 10^9 \times 3600}{50,000}\right) = \log_2(1.89 \times 10^{10}) \approx 34.137\text{ 位}$
   - 叠加 CAP=15 或 CAP=6 后，实际可计份额被直接砍掉 80% 以上，难度更是毫无悬念地死锁在最易边界。

## 9. 女巫成本量化与盈亏平衡模型

### 9.1 StakeVault 质押要求与时间锁机制分析

根据 `src/StakeVault.sol` 合约实现，参与 PoW 挖矿与份额提交的前置准入机制受以下严格条款约束：

1. **单地址质押门槛 (`DEPOSIT`)**：
   - 每个独立矿工地址必须调用 `deposit()` 并锁定正好 `DEPOSIT` 数额的 BNB（测试网与当前主网初始配置为 `0.01 BNB`，在治理可调区间 `[MIN_DEPOSIT = 0.001 BNB, MAX_DEPOSIT = 10 BNB]` 内）。
   - 合约在 `status(address u)` 中要求：地址必须具备有效质押（`stakes[u].has == true`）且未进入退出申请阶段（`stakes[u].withdrawReqEpoch == 0`）。
   - 矿工在 `MinerV1.submitShares` 中若质押状态为非活跃，将直接触发 `NotStaked()` 异常并拒绝提交。

2. **强制退出冷却锁定期 (`COOLDOWN_EPOCHS`)**：
   - 矿工申请赎回质押金必须调用 `requestWithdraw()`，合约记录请求生效轮次 `withdrawReqEpoch = uint64(epoch()) + 1`；
   - 赎回资金受不可跳过的冷却时间保护：
     $$\text{Cooldown} = \text{COOLDOWN\_EPOCHS} \times \text{EPOCH\_LEN} = 48 \times 3600\text{ 秒} = 48\text{ 小时 (2 整天)}$$
   - 在冷却期结束前调用 `withdraw()` 将直接触发 `CooldownActive()` 拒绝；
   - 一旦发起退出申请，该地址的挖矿活跃资格立即失效，无法继续参与后续轮次的份额提交与奖励分成。

3. **挖矿预热期与全生命周期资金锁定时间**：
   - 新地址质押入场后，受 `MinerV1` 的 24 轮（24 小时）预热期约束，其提交权重从 25% 线性增长至 100%；
   - 因此，一个女巫地址从**质押入场** $\rightarrow$ **满血挖矿** $\rightarrow$ **申请退出并取回资金**，其**最短不可撤销的资金锁定时间为 72 小时（3 天）**（24h 预热至满效 + 48h 退出冷却）。

### 9.3 盈亏平衡模型推导与敏感度分析

#### 1. 增量代币收益 (基于 SybilSimulation.t.sol)

在诚实矿工基准环境（100 名诚实矿工，每人提交 2 份份额，诚实总权重 $W_{\text{honest}} = 100 \times w(2) = 141,421,300$）下，攻击者拥有充沛算力，在 CAP=6 下不同拆分策略的表现如下：
- **单地址基准（1 地址打满 CAP=6）**：
  - 获得权重：$W_A = 1 \times w(6) = 2,449,489$（占比 $1.7025\%$）；
  - 单日代币产出（首日每日总配额 $D_0 = 3,000,000$ Token）：$R_A = 3,000,000 \times 1.7025\% \approx 51,075\text{ Token/天}$。
- **10 个女巫地址集群（打满 60 份份额）**：
  - 获得权重：$W_{10} = 10 \times 2,449,489 = 24,494,890$（占比 $14.7634\%$）；
  - 单日代币产出：$R_{10} = 3,000,000 \times 14.7634\% \approx 442,902\text{ Token/天}$；
  - 相对单地址的**每日增量代币数**：$\Delta R_{10} = 442,902 - 51,075 = \mathbf{391,827\text{ Token/天}}$。
- **100 个女巫地址集群（打满 600 份份额）**：
  - 获得权重：$W_{100} = 100 \times 2,449,489 = 244,948,900$（占比 $63.3974\%$）；
  - 单日代币产出：$R_{100} = 3,000,000 \times 63.3974\% \approx 1,901,922\text{ Token/天}$；
  - 相对单地址的**每日增量代币数**：$\Delta R_{100} = 1,901,922 - 51,075 = \mathbf{1,850,847\text{ Token/天}}$。

#### 2. 盈亏平衡核心公式

女巫攻击实质是一项资本与运营支出决策。要使拆分地址有利可图，每日新增产出的代币二级市场价值必须覆盖链上 Gas 沉没成本与质押资金的时间/机会成本：
$$\text{代币价格 } P \times \text{每天增量代币数 } \Delta R = \text{gas 成本 } C_{\text{gas}} + \text{锁定资金的机会成本 } C_{\text{opp}}$$

由此推导**盈亏平衡代币价格**：
$$P^* = \frac{C_{\text{gas}} + C_{\text{opp}}}{\Delta R}$$

各项参数定义：
1. $C_{\text{gas}} = \text{GasCost}_{\text{daily}}(N)$：单日链上净 Gas 支出（以 1 Gwei 为基准，10 地址为 $0.045628\text{ BNB/天}$，100 地址为 $0.456282\text{ BNB/天}$）；
2. $C_{\text{opp}}$：锁定资金的每日机会成本。设集群质押总额 $M = N \times \text{DEPOSIT}$（单位 BNB），年化机会成本率/无风险借贷利率为 $r_{\text{annual}}$（基准取常规 DeFi 收益率 $10\%$，即日化成本率 $r_{\text{daily}} = \frac{10\%}{365} \approx 0.0274\%$）：
   $$C_{\text{opp}} = M \times \frac{r_{\text{annual}}}{365} = (N \times \text{DEPOSIT}) \times \frac{r_{\text{annual}}}{365}$$
3. 对应估值指标：
   - **盈亏平衡全稀释市值 (FDV)**：$\text{FDV}^* = P^* \times \text{MAX\_SUPPLY} = P^* \times 1,000,000,000$；
   - **首日流通市值**：$\text{MCap}^*_{\text{circ}} = P^* \times 103,000,000$（初始预挖 1 亿 + 首日产出约 300 万）。

### 9.4 已知残余风险与主网 DEPOSIT 动态估值设定策略

#### 1. 已知残余风险 (Known Residual Risks)

通过上述盈亏平衡量化，本方案客观界定系统在防御女巫攻击时的能力边界与残余风险：

1. **高市值情景下的经济可行性逆转**：
   - 当代币在二级市场取得较高估值（例如 FDV 达到 100 万至 1000 万美元以上）时，代币二级市场单价远超 $0.00015 USD 的保本线；
   - 此时，100 个地址每日增量代币（1,850,847 Token）的市场价值可达 $1,850 至 $18,500 USD，而每日链上 Gas 沉没成本仅约 $274 USD。**在缺乏高额质押门槛的静态配置下，攻击者拆分地址能够获取显著的超额正收益**。
2. **非罚没机制下的资金本金安全感**：
   - `StakeVault` 当前设计为**无罚没（No-Slashing）质押模型**，质押金仅用于准入资格审查与退出时间锁；
   - 只要代币二级市场或 BNB 本身不出现单日腰斩等极端流动性崩盘，女巫攻击者在锁定 72 小时后仍能全额赎回质押 BNB 本金，因此其最大沉没成本仅为日常链上 Gas。
3. **因此，单纯依靠初始静态参数无法永久阻断女巫行为**：必须清醒认识到，CAP=6 与 0.01 BNB 初始质押并非“绝对安全锁”，而是一道在项目冷启动期与低流动性阶段有效保护诚实散户矿工的经济屏障。

#### 2. 主网 DEPOSIT 随代币估值动态设定机制

为持续压制高市值情景下的女巫拆分冲动，主网治理委员会与 Timelock 必须根据代币流通市值（MCap）与全稀释市值（FDV）建立**动态阶梯式质押调整准则**：

$$\text{DEPOSIT}_{\text{target}} = \min\left(\text{MAX\_DEPOSIT}, \max\left(\text{MIN\_DEPOSIT}, \frac{\text{单日挖矿产出总价值} \times \theta}{N_{\text{sybil\_cluster}} \times P_{\text{BNB}}}\right)\right)$$

其中 $\theta$ 为资本压制因子（建议取值 $\ge 2.0$），要求女巫集群锁定的本金总价值至少为单日产出总值的两倍以上，配合 48 小时提款冷却形成强约束。
